# 単語メモ — プロジェクト仕様

Claude Code がこのリポジトリで作業するときに読むファイル。
背景・技術選定の理由・仕様・守るべき原則をまとめる。

---

## 1. 背景（なぜ作ったか）

開発中に知らない技術用語に出会うたび、メモして後で調べる作業が発生していた。
この「調べる手間」を消すのが目的。

- 単語を放り込むだけで、AIが **意味・具体例・使い方** を自動生成する
- 生成された解説を PC・スマホから見返して学習する
- 利用者は **本人1名のみ**（ユーザー登録画面は作らない）

**アプリの性格**：メモ帳ではなく **単語帳**。
「メモを整理したい」ではなく「調べる手間を消したい」が動機。
機能追加を検討するときは、この一点に効くかで判断する。

---

## 2. 技術スタック

| 層 | 技術 | 選定理由 |
|---|---|---|
| コンテナ | Docker Compose（開発5サービス） | 環境差をなくす |
| バックエンド | Rails 8.1 / Ruby 3.3 | |
| フロントエンド | Vue 3 + Vite（SPA） | |
| DB | PostgreSQL 16 | |
| ジョブ / pub-sub | Sidekiq 8 + Redis 7 | 管理UIで非同期処理が可視化される |
| WebSocket | Action Cable（Redis アダプタ） | 生成完了をリアルタイム通知 |
| AI | Anthropic Claude Opus 4.8 + structured output | 解説品質がアプリの価値そのもの |
| 認証 | `has_secure_password` + httpOnly セッションCookie | 中身が読めて学習になる |
| テスト | RSpec + FactoryBot + WebMock | |
| デプロイ | Fly.io | |

### コンテナ構成

```
web    Rails（API・SPA入口HTML・Vite中継）    :3000
vite   Vite開発サーバー（HMR）※開発のみ      :3036
worker Sidekiq（AI呼び出しを別プロセスで実行）
db     PostgreSQL                            :5432
redis  ジョブキュー ＋ Action Cable の pub/sub
```

`vite` は開発専用。本番（Fly.io）は事前ビルド済みの静的ファイルを配信するため存在しない。
開発中に `vite` が落ちていると**画面が一切表示されない**（Rails は自前でJSを持たないため）。

#### HMR の通信経路（2系統に分かれる）

```
① アセット  ブラウザ → localhost:3000/vite-dev/... → Rails → vite:3036
② 更新通知  ブラウザ → ws://localhost:3036 → vite      （Railsを経由しない）
```

②が直結なのは、中継役の `ViteRuby::DevServerProxy` が `Rack::Proxy` 製で
WebSocket の Upgrade を扱えないため。中継させると画面は出るが自動更新だけが静かに止まる。
①を Rails 経由に保つことで、ブラウザから見たオリジンは 3000 のみで変わらない。

## 3. 設計判断とその理由

変更を加えるときは、以下の判断を覆していないか確認すること。
すべて意図的な選択であり、既定値だからではない。

| 判断 | 理由 | 覆すとどうなるか |
|---|---|---|
| 1レコード = 1単語 | 入力コストを最小化するため | 入力が面倒になり使われなくなる |
| AI生成は**非同期** | 生成に10秒かかる | Railsのリクエスト枠を占有し全体が詰まる |
| WebSocketで完了通知 | 非同期にすると完了を伝える手段が要る | ユーザーが手動リロードすることになる |
| **同一オリジン**（Rails が Vue を配信） | Cookie・CORS・wss がすべて素直になる | CORS + SameSite=None が必要になり CSRF 耐性が落ちる |
| Devise を使わない | 認証の中身を理解するのが目的 | ブラックボックスが増え、目的と矛盾する |
| セッションCookie（JWTではない） | httpOnly で XSS からトークンを守れる | localStorage の JWT は XSS で即座に盗まれる |
| `examples` は jsonb（正規化しない） | 単独で検索も更新もしないため | JOINが増えるだけで得るものが無い |
| **リトライは1層のみ**（`Llm::Client`） | 多層で重ねると指数的に課金が増える | 3×25 = 75回 呼び出して1単語250円超 |
| 復習機能（SRS）は作らない | 単語0件では設計も検証もできない | 使われない機能が保守対象として残る |
| Solid Queue ではなく Sidekiq | 実務遭遇率と可視化されたUI | |
| **フォルダは1単語1つ**（タグと別概念） | タグは平均3個付き30件で40〜50種に膨らみ、辿る軸にならない | ナビゲーションが破綻し探せなくなる |
| フォルダの分類は**AI呼び出しに相乗り** | 分類専用に呼ぶと1単語6.8円になる | 費用が倍増する |
| 新規フォルダは**AIに作らせず提案止まり** | 勝手に作るとフォルダが際限なく増える | タグと同じ末路をたどる |
| 既存フォルダへの割り当ては**黙って実行** | 毎回承認を求めると単語が増えるほど作業が増える | 「調べる手間を消す」に逆行する |
| 選択して調べた語も**通常の単語** | 解説内で分からなかった語こそ単語帳に入れるべき対象 | 別概念にすると後日また調べ直す |
| 選択からの登録は**確認を一段挟む** | 選択は事故が起きやすく、1タップ=3.4円かつ一覧に増える | 誤タップがそのまま課金とゴミ単語になる |
| 選択バーは**画面下部固定**（浮かせない） | スマホでOSの選択メニューと場所が競合する | ボタンが隠れて押せなくなる |
| HMRのアセットは**Rails経由**（Viteに直アクセスさせない） | 上の「同一オリジン」を崩さないため | 3036が別オリジンになりCORS設定が要る |
| HMRの**ws だけ**は 3036 に直結（例外） | Rack::Proxy が Upgrade を扱えず中継不能 | 画面は出るが自動更新だけ静かに止まる |

## 4. 守るべき原則

### セキュリティ

- **単語の取得は必ず `current_user.terms` から始める**
  `Term.find` と書くと権限チェックが消える。関連付け経由なら構造的に防げる。
  フォルダも同様に `current_user.folders` から始める。
- **`folder_id` / `source_term_id` は Strong Parameters に入れてよいが、所有者検証を外さない**
  どちらも利用者が指定する正当な値なので許可が要る。
  ただし他人のIDを送られると、自分のデータが他人の画面に現れる。
  `Term#folder_must_belong_to_same_user` と
  `Term#source_term_must_belong_to_same_user` が防いでいる。この検証を消さない。
- **他人のリソースには 403 ではなく 404 を返す**
  403 は「実在するが他人のもの」を教えてしまい、ID列挙を許す。
- **ログイン失敗のメッセージを分けない**
  メールアドレスの存在有無が漏れる。
- **AIの出力を `v-html` で描画しない**
  AIの出力は信用できない入力として扱う。`{{ }}` は自動エスケープされる。
- **Strong Parameters に `user_id` / `status` を追加しない**
  なりすましと状態改ざんが可能になる。
- **`.env` をコミットしない**
  公開リポジトリのAPIキーは数分でボットに悪用される。

### コスト

- リトライ回数を増やす変更は、**呼び出し回数 × 3.4円** で影響を試算してから行う
- `ExplainTermJob` は例外を再 raise しない（Sidekiqの自動リトライを起こさないため）
- 現状の使用量は `ApiCallLog.monthly_summary` で確認できる

### テスト

- 本物のAPIをテストで呼ばない（`Llm::Explainer.build` がテスト環境では Fake を返す）
- 権限境界（他人のデータが見えないこと）のテストは削除しない
- `RAILS_ENV` は `rails_helper.rb` で強制的に `test` にする（`||=` にしない）

### 見た目

**画面に手を入れる前に [docs/09-デザイン.md](../docs/09-デザイン.md) を読むこと。**
トークン（間隔・角丸・色・文字サイズ）と「してはいけないこと」がまとまっている。

要点だけ再掲する。詳細と理由はドキュメント側にある。

- **間隔は4pxの倍数**。`rem` で書く（`--space-*`）。`px` で余白を書かない
- **角丸は入れ子で4pxずつ減らす**（外 16 → 12 → 8 → 内 4）。例外を作らない
- **青は「操作できるもの」だけ**。面を青で塗らない
- **状態色（完了・生成中・失敗）を青にしない**。状態が伝わらなくなる
- **文字は 14px（`--text-sm`）を下回らせない**
- **アニメーションは「見落とすと困る変化」にだけ**。一覧の行とページ遷移には付けない
- 新しい色・サイズを直接書かず、まずトークンとして定義する

## 5. コメント方針

このリポジトリのコードには意図的に**多量のコメント**が入っている。
学習が目的のため、通常の実務基準より遥かに多い。

- **逐次コメント**：その行が何をしているか
- **`【なぜ】` コメント**：なぜその実装を選んだか、他の選択肢を採らなかった理由

コードを変更したら、対応するコメントも更新すること。
**古いコメントはコメントが無いより有害。**

## 6. よく使うコマンド

```bash
docker compose up -d                          # 起動
docker compose logs -f worker                 # ジョブの実行状況
docker compose logs -f vite                   # フロントのビルドエラー（画面が出ない時はまずここ）
docker compose exec web bundle exec rspec     # テスト
docker compose exec web rails console         # コンソール
docker compose exec web rails db:migrate      # マイグレーション

# gemを追加したら（イメージ再ビルドではなくこちら）
docker compose exec web bundle install && docker compose restart web worker

# npmパッケージを追加したら（viteの再起動が要る）
docker compose exec vite npm install && docker compose restart vite
```

- アプリ: http://localhost:3000
- Sidekiq管理画面: http://localhost:3000/sidekiq （要ログイン）

### HMRが効かなくなったときの切り分け

上から順に見る。**画面が出るかどうか**で原因が大きく分かれる。

| 症状 | 見るところ |
|---|---|
| 画面が真っ白／JSが404 | `docker compose logs vite`。viteが落ちていないか |
| 画面は出るが保存しても変わらない | ブラウザのコンソールでws接続エラーを確認。3036が公開されているか |
| 保存しても何も起きない（wsは正常） | 変更がコンパイル結果に影響していない可能性。テンプレート内の文言を変えて再確認 |
| ポートがずれた | `strictPort: true` にしてあるので、埋まっていればviteは起動失敗する。ログに出る |

### 開発中の注意

**`docker compose restart web worker` が必要な場面が3つある。**
どれも「テストは通るのに画面だけ動かない」という形で現れるので、
原因を探す前にまず再起動を試すとよい（テストは毎回新しく起動するため影響を受けない）。

- **`app/` 配下に新しいディレクトリを作ったとき**
  オートロードパスは起動時に確定するため、後から作ったディレクトリは
  読み込まれない（`app/serializers/` を追加したときに踏んだ）。
  症状: `uninitialized constant`
- **マイグレーションでカラムを足したとき**
  スキーマ情報が起動時にキャッシュされている。
  症状: `unknown attribute 'xxx' for Term`（`source_term_id` で踏んだ）
- **`app/` のコードを変えたとき（worker のみ）**
  Sidekiq は Rails と違い自動リロードしない。
  ジョブやサービスを直したのに挙動が変わらないときは、ほぼこれが原因。
