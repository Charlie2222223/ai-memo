# 非同期処理とWebSocket — ジョブキュー・pub/sub・Action Cable

このアプリで**最も実務的な部分**。「重い処理は裏に回して、完了をpushする」は
Webアプリで最頻出のパターンです。

---

## 1. なぜ非同期にするのか

AI解説の生成には **約10秒** かかります。これをHTTPリクエストの中で待つと：

```
[ブラウザ] POST /api/terms
   ↓
   ↓  ・・・ 10秒間ぐるぐる ・・・
   ↓  （Railsの1プロセスを占有し続ける）
   ↓
   200 OK
```

**問題点：**
- 画面が10秒固まる
- Railsが同時に処理できる枠（既定5本程度）を占有する
  → 5人が同時に登録しただけで、他のページすら開けなくなる
- スマホで電波が悪いとタイムアウトする
- タブを閉じたら生成結果が失われる

---

## 2. 正しい形

```
[ブラウザ] POST /api/terms
   ↓ 0.05秒で 201 が返る       [画面] カード「生成中…」
   ↓
[Rails] terms に保存(pending) → Redisにジョブを積む → 即座にレスポンス
                                    ↓
                          [Redis] ジョブの待ち行列
                                    ↓
                          [Sidekiq worker] ← 別プロセス・別コンテナ
                                    ↓ Claude API（10秒）
                                    ↓ terms を更新(completed)
                                    ↓ api_call_logs に記録
                                    ↓ 「できたよ」と放送
                          [Redis] pub/sub で中継
                                    ↓
                          [Rails] WebSocketで繋がっているブラウザへ転送
                                    ↓
                          [画面] カードが自動で解説入りに変わる
```

**HTTPリクエストは0.05秒で終わっている**のがポイントです。
残りは全部その外側で起きています。

該当コード：`app/controllers/terms_controller.rb#create` → `app/jobs/explain_term_job.rb`

## 3. Redis が2つの役割を持っている

同じミドルウェアが文脈によって別の役割を果たす、良い例です。

### 役割① ジョブキュー（待ち行列）

```
Rails  → 「この単語を解説しといて」とRedisに積む（publish ではなく push）
Sidekiq → Redisから取り出して実行（pop）
```

Redisに積むので、**Railsが再起動してもジョブは消えません**。

### 役割② pub/sub（放送設備）

```
[Railsプロセス]   ← ブラウザはこっちとWebSocketで繋がっている
[Sidekiqプロセス] ← AI呼び出しが終わったのはこっち
```

この2つは**完全に別のプロセス**（別コンテナですらある）。
メモリを共有していないので、直接は伝えられません。

```
Sidekiq → Redisに「terms_1が完成した」と投げる（publish）
Rails   → Redisを購読していて受け取る（subscribe）
Rails   → 繋がっているブラウザへWebSocketで流す
```

### だから cable.yml の development を変えた

Rails の初期値は `adapter: async` ですが、これは
**「同じプロセスの中でだけ通知が届く」**設定です。

このアプリは Rails と Sidekiq が別プロセスなので、`async` のままだと
**Sidekiqからの通知は誰にも届かず、カードが永遠に「生成中…」のまま止まります。**

しかもエラーにならず、静かに何も起きません。原因が非常に分かりにくい不具合です。

```yaml
development:
  adapter: redis    # ← async から変更
```

## 4. ジョブの引数は「IDだけ」渡す

```ruby
ExplainTermJob.perform_later(term.id)     # ✅
ExplainTermJob.perform_later(term)        # ❌
```

**理由**：ジョブの引数はRedisにJSONとして保存されます。
「積んだ時点」と「実行される時点」には時間差があり、
その間にレコードが更新されていると、**古い状態のオブジェクトで処理してしまいます**。

IDだけ渡して実行時にDBから読み直せば、必ず最新の状態が得られます。
Redisに保存されるデータも小さくなります。

> **原則：ジョブの引数は識別子を渡し、実体は実行時に取得する。**

## 5. 状態機械（status）

```
pending ──成功──> completed
   │                  │
   └──失敗──> failed ──再生成──> pending
```

**なぜ3状態が必要か**：この区別ができないと、画面が
「生成中」と「失敗」を出し分けられません。
ユーザーは永遠に「生成中…」を見せられて、待てばいいのか壊れているのか分かりません。

---

## 6. 冪等性 — 二重実行への備え

Sidekiqは **「少なくとも1回は実行する」** 保証（at-least-once）です。
ワーカーが処理中に強制終了すると、同じジョブがもう一度実行されることがあります。

```ruby
unless term.pending?
  Rails.logger.info("#{term.status} のためスキップします")
  return
end
```

これが無いと、完成済みの解説がもう一度生成され、
**無駄に課金された上、内容が入れ替わります。**

> ちなみに「冪等性」は、あなたが最初に例として挙げた単語です。
> このアプリの実装そのものが、その概念の実例になっています。

## 7. リトライは1つの層でだけ行う

これがこのアプリで**最もコストに直結する設計判断**です。

```
Llm::Client   … 3回リトライする（実装済み）
Active Job    … 既定でさらに5回
Sidekiq       … 既定で25回
```

全部有効だと、最悪 **3 × 25 = 75回** APIを呼びます。
1回3.4円なので、**1単語で250円超**。
APIが数時間不調なら、その間ずっと課金され続けます。

### 対策

```ruby
rescue StandardError => e
  term.apply_failure!(...)
  record_failure(...)
  # あえて再raiseしない ← Sidekiqのリトライを起こさない
end
```

失敗はDBに記録し、**ユーザーが画面の「再生成」ボタンで自分の意思で再実行**します。

自動リトライを増やすより、「失敗が見えて、手で押し直せる」方が
コストも制御でき、原因にも気付きやすい。

### さらにエラーを分類する

| 種類 | 例 | リトライ |
|---|---|---|
| 一時的な問題 | 429 レート制限、500 サーバー障害、接続エラー | ✅ する（待てば通る） |
| こちら側の問題 | 401 認証エラー、400 不正リクエスト | ❌ しない（何度送っても同じ） |

分類しないと、**APIキーを間違えただけで3倍の時間待たされ**、
本当の原因が「3回試したがダメ」というログに埋もれます。

実際にこのアプリを検証したとき、401 は **1回・262ms** で諦めました。

## 8. 失敗しても必ず通知する

```ruby
ensure
  broadcast_update(term)   # 成功でも失敗でも必ず実行される
end
```

**失敗を伝えることも機能のうち**です。
通知しないと画面は「生成中…」のまま止まり、ユーザーは何が起きたか分かりません。

## 9. WebSocketの購読で最も多い脆弱性

```ruby
def subscribed
  stream_for current_user    # ✅ サーバーが知っている事実
  # stream_for User.find(params[:user_id])   # ❌ 絶対にやらない
end
```

クライアントから送られた値で宛先を決めると、
**その値を書き換えるだけで他人の通知を受信できます。**

HTTPのAPIには権限チェックを書いても、**WebSocketだけ素通し**という実装は
実際によくあります。入口は全部塞ぐこと。
