## 1. 多対多と中間テーブル（最重要）

「1つの単語に複数タグ、1つのタグが複数の単語に付く」を表現したい。

### なぜ2テーブルでは無理か

**失敗案A：`terms` に `tag_id` を持つ**
```
| id | word   | tag_id |
| 1  | 冪等性 |   3    |  ← 1つしか付けられない
```

**失敗案B：カンマ区切りで持つ**
```
| 1  | 冪等性 | "3,7"  |
```
一見動くが必ず苦しむ：
- 「タグ3の単語」を探すのに `LIKE '%3%'` → タグ13, 23, 30 も引っかかる
- 索引が効かず、件数が増えると急激に遅くなる
- 存在しないタグIDを書いてもDBは検知できない
- タグを消しても文字列の中の値は残り続ける

### 正解：関係そのものをテーブルにする

```
term_tags
| term_id | tag_id |
|    1    |   3    |  ← 冪等性 に API設計
|    1    |   7    |  ← 冪等性 に インフラ
|    2    |   7    |  ← コンテナ に インフラ
```

**1行 = 「この単語にこのタグが付いている」という1つの事実。**

**多対多を見たら中間テーブル** — 実務のER図はほぼこの組み合わせでできています。
（学生↔授業＝履修、記事↔タグ、ユーザー↔グループ＝所属）

### 中間テーブルの必須ルール

```ruby
add_index :term_tags, [:term_id, :tag_id], unique: true
```

これを忘れると同じ組み合わせが2行できて、
**JOINした一覧で単語が2件に増える**（画面に同じカードが2枚出る）。
中間テーブルで最も忘れられ、最もバグを生む箇所です。

## 2. 正規化は「目的」ではなく「手段」

`examples`（AIが生成する例文の配列）は、正規化せず **jsonb カラム1本** にしています。

**正規化する価値があるのは次の場合：**
- その要素を単独で検索する
- その要素を単独で更新・削除する
- その要素に他テーブルから参照が張られる

例文はどれにも当てはまりません。常に単語と一緒に読まれ、単語ごと再生成され、
例文だけを検索することもない。

分けると JOIN が1つ増え、N+1問題の温床が1つ増えるだけです。

> **「分けると何が良くなるか」を答えられないなら分けない。**

一方、タグは分けています。単独で検索し（絞り込み）、複数の単語から参照されるからです。

## 3. N+1問題

一覧で単語50件とそのタグを表示するとき：

```ruby
# ❌ includes が無いと
terms = current_user.terms          # SELECT terms       … 1回
terms.each { |t| t.tags }           # SELECT tags × 50   … 50回
                                    # 合計 51回 = 1 + N
```

```ruby
# ✅ includes を付けると
terms = current_user.terms.includes(:tags)
# SELECT * FROM terms WHERE user_id = 1
# SELECT * FROM tags WHERE term_id IN (1,2,...,50)
# 合計 2回
```

**なぜ深刻か**：開発中はデータが5件なので気付きません。
本番でデータが増えてから急に遅くなる。「開発では速いのに本番で遅い」の代表的原因です。

## 4. インデックスの列の順序には意味がある

```ruby
add_index :terms, [:user_id, :word], unique: true
```

複合インデックスは **左から順にしか使えない**：

| 検索条件 | `(user_id, word)` の索引 |
|---|---|
| `user_id` だけ | ✅ 効く |
| `user_id` + `word` | ✅ 効く |
| `word` だけ | ❌ 効かない |

このアプリは常に「自分の単語の中から」探すので `user_id` が左で正解。
逆順にすると一覧表示で索引が効きません。

### なぜ `word` 単独のユニークではないのか

`word` 単独にすると、誰かが「冪等性」を登録した瞬間、
**他の全員が二度と登録できなくなります**。
一意であるべき範囲は「そのユーザーの中で」なので `user_id` と組にします。

## 5. モデルの検証とDB制約は両方書く

```ruby
# マイグレーション
t.string :email, null: false
add_index :users, :email, unique: true

# モデル
validates :email, presence: true, uniqueness: true
```

一見二重ですが、**役割が違います**。

| | 目的 | 効く範囲 |
|---|---|---|
| モデル側 | ユーザーに読めるエラーを返す | Rubyのコードを通ったときだけ |
| DB側 | データを壊さない最後の砦 | どんな経路でも |

**モデル側だけでは足りない理由（競合状態）：**

```
時刻1  Aのリクエスト: SELECT → 居ない！
時刻2  Bのリクエスト: SELECT → 居ない！
時刻3  Aのリクエスト: INSERT → 成功
時刻4  Bのリクエスト: INSERT → 成功（重複した）
```

`validates uniqueness` は「保存前にSELECTして確認」する実装なので、
確認と挿入の間に隙間があります。DB側の制約にはこの隙間がありません。

## 6. 金額は整数で保存する

```ruby
t.integer :cost_micro_usd   # 1マイクロUSD = 0.000001ドル
```

**float（小数）を使ってはいけない理由：**

```ruby
0.1 + 0.2          # => 0.30000000000000004
(0.1 + 0.2) == 0.3 # => false
```

1件なら僅かな誤差ですが、何千件も合計すると金額が合わなくなります。
「1円合わない」の典型的な原因。

**最小単位の整数で保存し、表示するときだけ割る。**
（日本円なら「銭」、ドルなら「セント」や「マイクロドル」）

## 7. 削除したときの振る舞い

| 関連 | 設定 | 挙動 |
|---|---|---|
| user → terms | `dependent: :destroy` | ユーザーを消すと単語も消える |
| term → term_tags | `dependent: :destroy` | 単語を消すと結び付きも消える |
| term → **tags** | **付けない** | 単語を消してもタグは残す |
| term → api_call_logs | `on_delete: :nullify` | 単語を消しても記録は残し、term_id を NULL に |

**`tags` に `dependent: :destroy` を付けてはいけない理由**：
単語を1つ消しただけで、そのタグが他の単語からも消えてしまいます。

**`api_call_logs` を残す理由**：
会計・監査の性格を持つ記録は原則として消しません。
「今月いくら使ったか」は、その後に単語を消したかどうかとは無関係です。
