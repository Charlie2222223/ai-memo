# 認証 — bcrypt・セッション・CSRF・SameSite

なぜ Devise を使わなかったか、から始めます。

---

## 0. なぜ Devise を使わないのか

Devise は Rails の認証gemの定番で、5行書けばログイン画面が生えてきます。
しかし**このプロジェクトでは意図的に使いません**。

> Devise は「認証を理解しなくても認証が動く」ためのgem。
> セッションがどう張られ、パスワードがどうハッシュ化され、
> Cookieに何が入っているかは全部隠されます。

このアプリの目的は「ロジックを知り、ツッコめる知識をつける」ことでした。
Devise はその真逆に働きます。

**gemは「自分で書くと事故る所」に使うもので、「学びたい所」に使うものではありません。**

実際に書いたコードは50行程度です（`app/controllers/concerns/authentication.rb`）。

## 1. パスワードは「ハッシュ化」であって「暗号化」ではない

| | 元に戻せるか | 用途 |
|---|---|---|
| 暗号化 | ✅ 鍵があれば戻せる | 後で読む必要があるもの |
| **ハッシュ化** | ❌ 原理的に戻せない | パスワード |

**パスワードは元に戻す必要がありません。**
照合は「入力値を同じ手順で潰して、保存値と一致するか見る」だけでできます。

だから戻せない方式を使う。
→ **DBが丸ごと漏れても、パスワードそのものは分からない。**

### 保存される値の読み方

```
$2a$12$N9qo8uLOickgx2ZMRZoMye.IjPeKYb3sVjkR1FEbA3rTLQfaCz1Aq
 ~~~ ~~ ~~~~~~~~~~~~~~~~~~~~~~ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  │   │           │                        └ ハッシュ値
  │   │           └ ソルト（22文字）
  │   └ コスト（2^12 = 4096回 繰り返す）
  └ アルゴリズム（2a = bcrypt）
```

### ソルトの役割

**同じパスワードでも、保存される値は毎回違います。**

```ruby
a = User.create!(password: "same-password-1")
b = User.create!(password: "same-password-1")
a.password_digest != b.password_digest   # => true
```

ソルトが無いと：
- DBを見るだけで「この2人は同じパスワード」と分かる
- よくあるパスワードのハッシュ一覧表（レインボーテーブル）で一括解読できる

ソルトがあると、一覧表はソルトごとに作り直しになり、事実上使えません。

### なぜ bcrypt は「わざと遅い」のか

普通のプログラムは速い方が良いのですが、パスワードのハッシュは逆です。

攻撃者はDBを盗んだ後、候補を片っ端から試します。
その速度は「1秒に何回ハッシュ計算できるか」で決まります。

| | 1秒あたりの試行回数 |
|---|---|
| SHA-256（高速なハッシュ） | 数十億回 |
| **bcrypt（コスト12）** | **数十回** |

1億倍以上の差。正規のログインは1回0.2秒で誰も困りませんが、
総当たり攻撃には現実的でない時間がかかります。

PCが速くなったらコストを上げて、攻撃コストを保ち続けられる設計です。

## 2. ログイン処理で絶対に忘れてはいけないこと

```ruby
def sign_in(user)
  reset_session           # ← これ
  session[:user_id] = user.id
end
```

### セッション固定攻撃（Session Fixation）

`reset_session` が無いと成立します：

```
① 攻撃者が先にサイトを訪れ、セッションID "abc123" をもらう
② 被害者にそのIDを固定させる細工をする
③ 被害者がそのIDのままログインする
④ サーバーは "abc123" にログイン済みの印を付ける
⑤ 攻撃者は自分が持っている "abc123" でアクセス
   → ログイン済みとして扱われ、なりすまし成立
```

**ログインの瞬間にセッションIDを作り直せば、攻撃者が知っている古いIDは無効になります。**

「ログイン成功時は必ずセッションを作り直す」は認証実装の鉄則です。

## 3. CSRF（クロスサイトリクエストフォージェリ）

Cookie認証を使う以上、必ず対策が要ります。

### 攻撃の流れ

```
① あなたが memo.fly.dev にログイン済み（Cookieを持っている）
② 別タブで攻撃者のサイト evil.example を開く
③ そのページにこんなHTMLが仕込まれている：

   <form action="https://memo.fly.dev/api/terms/1" method="post">
     <input name="_method" value="delete">
   </form>
   <script>document.forms[0].submit()</script>

④ ブラウザは memo.fly.dev 宛なのでCookieを自動で付けて送信
⑤ サーバーから見ると「本人の正規のリクエスト」に見える
   → あなたの単語が勝手に削除される
```

**ポイント：攻撃者はCookieを読めないが、送らせることはできる。**

### 対策の仕組み

サーバーが発行した予測不能なトークンを、リクエストに含めさせます。

```html
<!-- レイアウトの csrf_meta_tags が出力する -->
<meta name="csrf-token" content="aRBvzoorbnE_KNBPjbHO...">
```

```javascript
// app/frontend/lib/api.js
headers: { 'X-CSRF-Token': csrfToken() }
```

**なぜ破られないか**：
攻撃者は別オリジンなので、同一オリジンポリシーにより `memo.fly.dev` のHTMLを読めません。
→ トークンの値を知る手段が無い → トークン付きのリクエストを作れない。

### 実際に確かめる

```bash
# トークン無しでPOST → 422
curl -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/api/terms \
  -H "Content-Type: application/json" -d '{"term":{"word":"test"}}'
```

Cookieを持っていても、トークンが無いだけで拒否されます。

## 4. SameSite — 構造的なCSRF対策

CSRFトークンとは別の、より根本的な防御です。

```ruby
same_site: :lax
```

| 値 | 挙動 |
|---|---|
| `:strict` | 他サイトからの遷移では一切Cookieを送らない（安全だが不便） |
| **`:lax`** | 普通のリンク（GET）なら送るが、**POST/DELETEには送らない** |
| `:none` | 常に送る（実質無防備。Secure必須） |

`:lax` なら、攻撃者のページから勝手にPOSTされても**Cookieが付かない**ので、
サーバーは未ログインとして扱います。

### 同一オリジンにした効果がここに出る

フロントとAPIを別ドメインに分けていたら、
正規のリクエストすら「他サイトから」の扱いになり、`:none` にせざるを得ませんでした。
**＝ CSRFへの構造的な防御を自ら捨てることになっていた。**

## 5. httpOnly — XSSからの防御

```ruby
httponly: true
```

**JavaScriptからCookieを読めなくします。**

### このアプリ特有のリスク

AIが生成した解説文をそのまま画面に表示します。
もしAIの出力に `<script>` が混ざり、それをHTMLとして埋め込むと実行されてしまいます（XSS）。

httpOnly が無い場合：
```javascript
document.cookie  // 全Cookieを読み取り → 攻撃者のサーバーへ送信 → セッション乗っ取り
```

httpOnly なら `document.cookie` に一切現れません。

### JWT を選ばなかった理由がこれ

| | 保存場所 | XSS時 |
|---|---|---|
| セッションCookie + httpOnly | JSから読めない場所 | **トークンは守られる** |
| JWT + localStorage | JSから読める場所 | 即座に盗まれる |

SPAの記事では JWT + localStorage をよく見かけますが、
**同一オリジンならセッションCookieの方が安全**です。

なお防御は多層で持ちます。Vue側では `v-html` を使わず `{{ }}`（自動エスケープ）で描画しています。

## 6. セキュアバイデフォルト

```ruby
class ApplicationController < ActionController::Base
  before_action :require_authentication   # ← 全体に掛ける
end

class SessionsController < ApplicationController
  skip_before_action :require_authentication, only: [:create, :show]  # ← 個別に外す
end
```

**逆向き（必要な所にだけ認証を書く）にしない理由：**

新しいコントローラを追加したとき、書き忘れた場所が誰でも見られる状態になります。

| 設計 | 書き忘れたとき |
|---|---|
| 必要な所にだけ書く | **公開されてしまう**（危険側） |
| **全体に掛けて個別に外す** | **ログインが必要になる**（安全側） |

人間は必ず書き忘れます。**書き忘れたときにどちらへ倒れるか**で設計を決めます。

## 7. エラーメッセージを親切にしない

```ruby
render json: { error: "メールアドレスまたはパスワードが違います" }
```

「メールアドレスが存在しません」と返すと、
攻撃者はアドレスを次々送って**どれが登録済みか**を調べられます（列挙攻撃）。

登録済みと分かれば、そのアドレスに絞ってパスワードの総当たりやフィッシングができます。

**親切さとセキュリティが正面から対立する場面**で、ログイン画面ではセキュリティを優先します。

この判断は `spec/requests/sessions_spec.rb` のテストで固定してあります。
将来「親切にしよう」と分けてしまう改変を、テストが止めてくれます。
