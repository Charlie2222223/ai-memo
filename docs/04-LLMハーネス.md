# LLMハーネス — AIアプリの品質はここで決まる

---

## 0. 「ハーネス」とは

語源は**馬具のハーネス（引き具）**。馬そのものではなく、
馬に装着して**力を取り出すための装具**です。

ソフトウェアでも同じ意味で、**本体ではなく、それを実用に耐える形にする周辺の足場**を指します。

```
             ┌────────── ハーネス（自分で書く部分）──────────┐
  「冪等性」→│ プロンプト組立 → API呼出 → JSONパース → 保存  │→ DB
             │      ↑            ↑          ↑              │
             │  system prompt  リトライ  バリデーション      │
             │  出力スキーマ   タイムアウト 失敗時の記録      │
             │  Fake差替      トークン計測                  │
             └───────────────────────────────────────────┘
                              ↑
                    Claude API（既製品・触れない）
```

**モデル以外の全部がハーネス。**
そして**AIアプリの品質はモデルよりハーネスで決まります。**
同じ Opus 4.8 でも、プロンプトが雑・リトライがない・パース失敗で落ちる、なら使い物になりません。

## 1. ファイル構成と責務

```
app/services/llm/
├─ client.rb            API呼出・リトライ・計測          ← HTTPを知っている層
├─ prompts/
│   └─ explain_term_v1.rb   プロンプト＋出力スキーマ      ← 「何を聞くか」
├─ explanation.rb       生成結果の値オブジェクト
├─ usage.rb             計測結果＋コスト計算
├─ explainer.rb         インターフェース（取り決め）
├─ claude_explainer.rb  本番実装
└─ fake_explainer.rb    テスト実装
```

**1クラス1責務**にしておくと、
「リトライの挙動を変えたい」ときに読む場所が1つに定まります。

## 2. structured output（出力形式の強制）

```ruby
output_config: {
  format: { type: "json_schema", schema: SCHEMA }
}
```

### なぜ必須か

プロンプトで「JSONで答えて」とお願いするだけだと、一定確率で：

- 前後に「はい、承知しました」が付く
- ` ```json ` で囲まれる
- キー名が変わる（`meaning` が `definition` になる）
- 日本語の引用符が混ざってJSONとして壊れる

**1%の失敗でも、100単語登録すれば1回は必ず遭遇します。**

スキーマを指定すると、API側が生成の各ステップで
「この形に沿う出力しか作れない」よう制約するため、構造的に壊れません。

### スキーマの書き方のコツ

```ruby
properties: {
  meaning: {
    type: "string",
    description: "この単語の意味を、専門用語を避けて2〜4文で説明する。..."
  }
}
```

**`description` は人間向けのコメントではなく、AIへの指示です。**
ここに「何文で」「誰向けに」を書くと、出力が安定します。

`additionalProperties: false` … 書いていないキーを出力させない
`required` に全部書く … 「あるかないか分からないキー」を無くす

## 3. プロンプトをファイルとバージョンで管理する

```ruby
VERSION = "explain_term_v1"
```

**プロンプトはAIアプリにおけるアルゴリズムです。**
コードの中に文字列で埋め込むと：

- どこにあるか分からなくなる
- 変更履歴が他の変更に埋もれる
- 「前の版に戻したい」ができない

ファイルに分け、`api_call_logs.prompt_version` に記録しておけば、
**v1 と v2 でトークン量・失敗率・所要時間がどう変わったかを数字で比較できます。**

これが無いと「なんとなく良くなった気がする」で終わります。

### system と user を分ける理由

| | 内容 | 変わるか |
|---|---|---|
| system | 「あなたは誰で、どう振る舞うか」 | 毎回同じ |
| user | 「今回何をしてほしいか」 | 毎回変わる |

同じ接頭辞は **prompt caching** が効いて、約1/10の料金になります。
混ぜると、AIがどちらを優先すべきか判断できなくなる問題もあります。

### 読み手を具体的に指定する

```
読み手は実務1年目のWebエンジニアで、HTML/CSS/JavaScript/HTTPの基礎は
理解していますが、設計・インフラ・DBの専門用語には不慣れです。
```

「分かりやすく説明して」だけでは、AIは基準を持てません。
読み手を決めると、前提として使ってよい語彙の範囲が定まり、出力が安定します。

## 4. リトライとエラー分類

```ruby
RETRYABLE_ERRORS = [RateLimitError, InternalServerError, APIConnectionError, APITimeoutError]
FATAL_ERRORS     = [AuthenticationError, PermissionDeniedError]
```

| 種類 | 意味 | 対応 |
|---|---|---|
| 一時的 | 429 / 500 / 接続断 | **待てば通る** → リトライ |
| こちら側 | 401 / 400 / 404 | **何度送っても同じ** → 即諦める |

分類しないと、APIキーを間違えただけで3倍待たされ、
原因が「3回試したがダメ」というログに埋もれます。

### 指数バックオフ

```ruby
delay = BASE_DELAY_SECONDS * (2 ** (attempt - 1))   # 1秒 → 2秒 → 4秒
```

等間隔だと、サーバーが高負荷のときに全クライアントが同じ間隔で再送し、
負荷が下がらず復旧を遅らせます（サンダリングハード問題）。

### SDKのリトライを切る

```ruby
Anthropic::Client.new(api_key: ..., max_retries: 0)
```

SDKは既定で2回リトライします。その上で自分でも3回やると
**最悪 3 × 3 = 9回**。課金は呼んだ回数だけ発生します。

> **リトライは1つの層でだけ行う。多層で重ねない。**

このアプリでは `Llm::Client` に一本化しています（試行回数をログに残したいため）。

## 5. 依存性の注入（DI）とFake

```ruby
def self.build
  Rails.env.test? ? FakeExplainer.new : ClaudeExplainer.new
end
```

**なぜ必要か**：ジョブが `ClaudeExplainer` を直接呼ぶと、
テストのたびに本物のAPIを叩くことになります。

- 毎回課金される
- 1回10秒かかる → テストが遅い → 誰も走らせなくなる
- 返答が毎回違う → 同じコードなのに通ったり落ちたりする
- **「APIが500を返したとき」を再現できない**（本物はわざと壊れてくれない）

最後が特に重要です。**異常系こそテストしたいのに、本物では異常を起こせません。**

間に「取り決め（インターフェース）」を挟むと、実装を差し替えられます。

```ruby
# 異常系テスト：必ず失敗するFakeを差し込む
failing = Llm::FakeExplainer.new(raise_error: Llm::Client::Error.new("rate limited"))
allow(Llm::Explainer).to receive(:build).and_return(failing)
```

### Fakeは本物と同じ形を返すこと

```ruby
usage = Usage.new(model: "fake-model", input_tokens: 100, ...)
```

Fakeが `nil` を返すと、コスト記録の処理だけテストされないまま残ります。

## 6. コスト管理

### 単価（100万トークンあたり）

| モデル | 入力 | 出力 |
|---|---|---|
| Opus 4.8 | $5 | $25 |
| Sonnet 5 | $3 | $15 |
| Haiku 4.5 | $1 | $5 |

**出力が5倍高い**のは、入力は並列に読めるが出力は1トークンずつ順に生成するため。
コストを下げたいときは、まず**出力を短くする**のが効きます。

### 1単語あたりの実測

```
入力 ≒ 500トークン × 5マイクロUSD  =  2,500
出力 ≒ 800トークン × 25マイクロUSD = 20,000
                          合計 22,500 マイクロUSD = $0.0225 ≒ 3.4円
```

### 金額は整数で保存する

```ruby
t.integer :cost_micro_usd   # 1マイクロUSD = 0.000001ドル
```

float を使うと `0.1 + 0.2 != 0.3` の誤差が積み上がります。
**整数のまま計算し、表示するときだけ割る。**

### 確認する

```bash
docker compose exec web rails runner 'pp ApiCallLog.monthly_summary'
```

```
{月: "2026-07", 呼び出し回数: 42, 成功: 40, 失敗: 2,
 入力トークン: 21000, 出力トークン: 33600,
 合計コストUSD: 0.945, 平均所要時間ms: 9200}
```

**見るのが簡単だと、実際に見るようになります。** コスト管理は習慣がつくかが全てです。

## 7. AIの出力は「信用できない入力」

- **`v-html` で描画しない**（`{{ }}` は自動エスケープ）
- **`Explanation.from_api` で形を整える**（`Array()` で配列を保証、タグは5個まで）
- **JSONパースを保護する**（`max_tokens` に達して途中で切れる可能性は残る）

ユーザーの入力を信用しないのと、まったく同じ理由です。

## 実験してみる

```ruby
# rails console で、プロンプトを変えて結果を比べる
c = Llm::ClaudeExplainer.new
explanation, usage = c.call(word: "冪等性", context: "API設計の記事で見た")
puts explanation.meaning
puts "コスト: #{usage.cost_usd} USD / #{usage.latency_ms}ms"
```

`effort` を `"medium"` から `"high"` に変えて（`client.rb`）、
品質とコストがどう変わるか比較してみてください。
